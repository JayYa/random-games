# 一个主题 = 一个 CSV + 一段文案，清单写在代码里

站点从单一的"今天吃什么"扩成三个主题（吃 / 玩 / 干）。一个主题由两部分构成：`public/` 下一个与它同名的 CSV（`eat.csv` / `play.csv` / `work.csv`），以及 `src/themes.ts` 里的一条记录（slug、CSV 文件名、转盘页标题、首页入口的说法、结果卡片上那句话）。首页是主题选择页，点进去用 hash 路由跳到 `#/eat` 这样的转盘页；未知的 hash 回落到首页。

## Considered Options

- **一个 CSV 加一列 `theme`**：省两次 `fetch`，但"名单"就从"一个文件"变成"一个文件的一个切片"。[ADR-0001](./0001-csv-in-repo-no-backend.md) 要求解析错误必须指出行号让人照着改，而混合文件里的行号对应不上使用者心里的那份名单；并且一个主题写坏一行会连带另外两个主题一起转不起来。
- **主题清单也做成 `public/themes.json`**：看着更"数据驱动"，实则给站点添了一个新的失败模式（清单取不到 / 写坏了，首页连按钮都渲染不出来），而这个文件的读者本来就是写代码的人。放在 `public/` 的东西只应该是给非程序员改的名单。
- **history 路由（`/random-games/play`）**：站点部署在 GitHub Pages 的项目子路径下，纯静态托管，刷新会 404。
- **不做路由，点主题直接换 DOM**：最省事，但刷新回到首页、后退键直接退出站点、也没法把"今天玩什么"的链接发给别人。

## Consequences

- 加第四个主题 = 写一个 CSV + 加一条 `themes.ts` 记录，不改任何其他代码。
- 主题只带面向使用者的四条文案。**错误提示一律用中性的"候选"，不随主题变**：错误页的读者是去改 CSV 的人，不是转转盘的人。这让加主题的文案成本减半。
- 转盘页和错误页都带一个回到首页的入口。分享出去的链接直接落在转盘页上，页面上必须有线索说明还有别的主题；名单写坏的主题也不该把人困在死路上。
- 每次只取当前主题的 CSV。首页不读任何名单，因此不知道哪个主题的名单是坏的，也就无法提前把它置灰——代价是坏名单要等点进去才发现，换来的是"取名单 → 解析 → 转盘或错误页"这条链路对每个主题各自独立。
- 站点不记住上次选的主题（与 [ADR-0004](./0004-wheel-has-no-memory.md) 同一口径）：直达某个主题靠 URL 书签，不靠程序替人记。
