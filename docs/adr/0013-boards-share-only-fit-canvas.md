# 两个盘面只共用对齐画布，帧循环各归各

转盘和弹球机作画前都经对齐画布（`src/fitCanvas.ts`）拿上下文：把画布的像素缓冲对齐到封顶后的设备像素比，交回按 CSS 像素设好变换的上下文。两个盘面共用的只有这一步；帧循环、尺寸观察与拆卸不共用，仍归各自的盘面。

理由是两边的帧循环策略正好相反。转盘按需要帧：静止时不跑 rAF，只在转的时候跑，并在揭晓、抹掉、尺寸或像素比变化时补画一帧。弹球机的风车一直在转，rAF 常转，尺寸变了下一帧自然画对。把两者收成一个驱动，只会多出一个「要不要常转」的开关，把差异挪进参数，驱动本身是浅的。揭晓、复位、焦点去向与输入绑定（转盘的「转」与按钮的锁、弹球机的柱塞指针）又各属各的盘面，收进驱动就把它和开抽、DOM 事件搅在一起。对齐像素缓冲则不同：宽度为 0 就不画、像素比封顶到 3、缓冲尺寸没变就不写、按像素比设变换，这几条两边完全一样，又都属于「写错了肉眼极难发现」那一类，值得只有一处实现、在 node 下逐条有用例。

## Considered Options

- **共用帧循环加尺寸观察的画布驱动**：两个盘面的帧循环一个按需、一个常转，驱动只能靠一个开关分叉，省下的代码不比多出来的参数多，却让改一边的帧循环有可能波及另一边。
- **接收机器与作画函数、直接交出挂载结果的整个盘面外壳**：揭晓、抹掉、复位、焦点去向和输入绑定都得穿过外壳，外壳就同时管着开抽转交与 DOM 事件，接口比两个盘面各自的渲染层加起来还宽。

## Consequences

- **像素缓冲的规则只有一处**：原来只管「封顶到 3」的像素比小模块并进对齐画布、删除；两块画布不会一块封顶、另一块不封，也不会在奇数像素比下差一个像素。
- **坐标系各归各**：对齐画布交回的是 CSS 像素。转盘照 CSS 像素作画，字号与线宽的 CSS 像素下限继续成立；弹球机自己再缩放到盘面坐标、上移可视区域顶部，作画函数照旧直接用盘面常量。
- **弹球机没有尺寸观察不是缺陷**：rAF 常转，尺寸或像素比变了下一帧就画对。转盘静止时不要帧，所以它得自己观察尺寸与像素比、补画一帧。
- **加下一个玩法**：直接用对齐画布拿上下文，帧循环、尺寸观察与拆卸自己写。
- **什么时候重新打开**：出现第三个玩法，且它的帧循环与现有某一方同形（同为按需或同为常转）时，才值得再看要不要把那一种帧循环收成共用的。
